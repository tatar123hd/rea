## สิ่งที่ต้องทำก่อนเริ่ม (2 อย่าง)

1. **แทนที่ `BAU_TMP`** ด้วยชื่อ data source จริงของลิสต์ BAU ในทุกไฟล์
   (Power Apps ไม่รองรับการตั้ง alias ชื่อจึงถูกเขียนตรง ๆ ในสูตร)
2. **เลือกชุดสูตร BAU** ระหว่าง **ชุด PERSON** กับ **ชุด TEXT**
   ตามชนิดจริงของคอลัมน์ `Responder` / `LM` — มองหาเครื่องหมาย `<<< ชุด ... >>>`
   ใน `shared/LoadData.pafx.txt` และ `screens/scrMyTasks.pa.yaml`
   วิธีตรวจชนิดคอลัมน์อยู่ใน `01-assumptions-architecture.md` หัวข้อ 1.3

## หลักการออกแบบที่สำคัญที่สุด

> **ดึงด้วย query ที่ delegate ได้ 100% ให้ได้ชุดข้อมูลเล็กพอก่อน (ช่วงวันที่ + แผนก)
> แล้วค่อยกรองละเอียดในหน่วยความจำ**

ทุกเงื่อนไขที่ส่งไป SharePoint เป็น `=` `<>` `<=` `>=` `>` หรือ `StartsWith`
บนคอลัมน์ที่ถูก index แล้วเท่านั้น ไม่มี `Search()`, ไม่มี `in` กับ data source,
ไม่มี `CountRows` ทั้งลิสต์ และไม่มี lookup ซ้อนใน gallery

หน้า **ตาราง** ใช้ keyset paging บนคอลัมน์ `ID` จึงเดินหน้าได้ไม่จำกัดจำนวนแถว
โดยไม่พึ่ง data row limit

## ข้อจำกัดที่ต้องรู้ก่อนใช้งานจริง

- ตัวเลขบนหน้า **ภาพรวม** นับเฉพาะในช่วงวันที่ที่เลือก ไม่ใช่ยอดรวมทั้งระบบ
- การเรียงลำดับข้ามหน้าในตารางทำได้เฉพาะตามลำดับการสร้าง (`ID`)
- ลิสต์ BAU **ต้อง** ถูก index ที่ `StartDate` `EndDate` `Status` ก่อนจะโตเกิน 5,000 รายการ
- ชุดคำสั่ง LoadData ถูกวางไว้ 2 ที่ ต้องแก้พร้อมกันเสมอ

รายการเต็มอยู่ใน `05-verification-and-test-plan.md` หัวข้อ 5.7

## ข้อความแจ้งความโปร่งใส

เอกสารและโค้ดชุดนี้เขียนโดย AI **ไม่ได้รัน Power Apps, ไม่ได้ต่อ SharePoint,
ไม่ได้รันสคริปต์ PowerShell และไม่ได้วัดประสิทธิภาพใด ๆ**
สิ่งที่ตรวจแล้วคือความสอดคล้องของชื่อคอลัมน์ ชื่อ named formula และการไล่อ่านสูตรทีละจุด
รายการตรวจที่ทำจริง และรายการที่ยังต้องทดสอบเอง อยู่ใน `05` หัวข้อ 5.1 และ 5.2
