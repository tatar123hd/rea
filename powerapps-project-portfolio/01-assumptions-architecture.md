## 1.2 คำถามที่ต้องการคำตอบ (ไม่บล็อกการสร้าง แต่กระทบผลลัพธ์)

1. **Q1 — ชื่อ BAU list จริง** ตอนนี้ใช้ `BAU_TMP` เป็น placeholder
2. **Q2 — ชนิดคอลัมน์ Responder / LM / Status** (ดูวิธีตรวจ §1.3)
3. **Q3 — "แผนก" ของโปรเจกต์** ผมใช้ department ของ *ผู้สร้างโปรเจกต์* ตอนที่กดสร้าง และ **ไม่** อัปเดตอัตโนมัติถ้าผู้สร้างย้ายแผนก ถ้าต้องการให้ย้ายตาม ต้องเพิ่มปุ่มให้ admin แก้
4. **Q4 — BAU กับแผนก** BAU list ไม่มีคอลัมน์แผนก ผมอนุมานแผนกจาก Responder/LM ผ่าน Office 365 Users ซึ่ง **delegate ไม่ได้** (ดู §1.5) ถ้าเจ้าของลิสต์ BAU ยอมเพิ่มคอลัมน์ `Department` ให้ จะเร็วและแม่นกว่ามาก — แต่ตามข้อกำหนด "ห้ามแก้โครงสร้าง BAU" ผมจึงไม่ทำ
5. **Q5 — การโอนความเป็นเจ้าของโปรเจกต์** เมื่อเจ้าของลาออก ใครรับช่วง (ดูตัวเลือกใน §1.10)
6. **Q6 — จำนวนโปรเจกต์ที่เปิดพร้อมกันจริง ๆ** ถ้าเกิน ~300 โปรเจกต์ที่ active พร้อมกัน แนะนำเพิ่มลิสต์สรุป (§1.5 ทางเลือก C)

## 1.3 วิธีตรวจชนิดคอลัมน์ BAU โดยไม่แตะแอปอื่น (อ่านอย่างเดียว ปลอดภัย 100%)

1. เปิดลิสต์ BAU ในเบราว์เซอร์
2. มุมขวาบน → **Settings (ฟันเฟือง)** → **List settings**
3. เลื่อนลงไปที่ตาราง **Columns** จะเห็นคอลัมน์ `Responder`, `LM`, `Status` พร้อมคอลัมน์ **Type**
   - `Person or Group` → ใช้สูตร **ชุด Person**
   - `Single line of text` → ใช้สูตร **ชุด Text**
   - `Choice` (สำหรับ Status) → เทียบด้วย `.Value`
4. **อย่ากดชื่อคอลัมน์** (จะเข้าหน้าแก้ไข) แค่ดูในตารางพอ

> หมายเหตุความถูกต้อง: ชื่อเมนู SharePoint เปลี่ยนบ่อย ถ้าไม่เห็น **List settings** ให้ลอง
> **Settings → List settings** หรือ **…** → **Settings** ตรวจชื่อปัจจุบันได้จากหน้า Microsoft Learn
> "Create a list in SharePoint"

วิธีสำรอง (ไม่ต้องมีสิทธิ์ตั้งค่า): ใน Power Apps Studio หลังเพิ่ม data source แล้ว พิมพ์ในสูตรว่า
`First(BAU_TMP).Responder.` แล้วดูว่า IntelliSense แนะนำ `.Email`, `.DisplayName` ขึ้นมาหรือไม่
— ถ้ามี = Person column, ถ้า `First(BAU_TMP).Responder` คืนสตริงเลย = Text column

ความสัมพันธ์ทั้งหมดใช้ **คอลัมน์ Number ที่ index แล้ว** (`ProjectID`, `PhaseID`) ไม่ใช่ Lookup column

### ทำไมใช้ Number แทน Lookup column

| ประเด็น | Lookup column | Number column (เลือกใช้) |
|---|---|---|
| Delegation ของ `Filter(Tasks, ProjectID = 12)` | Lookup ต้องเทียบ `ProjectID.Id` ซึ่งเป็น sub-field — Power Apps มักเตือน delegation และ SharePoint connector รองรับไม่ครบ | `=` บน Number ที่ index แล้ว delegate ได้แน่นอน |
| Index | index lookup ได้ แต่ query ซับซ้อนกว่า | index ตรงไปตรงมา |
| ลิสต์ > 5,000 | Lookup column บนลิสต์ใหญ่โดน list view threshold บ่อย | ปลอดภัยกว่า |
| ข้อเสีย | — | ไม่มี referential integrity ให้อัตโนมัติ — แอปต้องลบลูกเองเมื่อลบแม่ (ทำแล้ว ดู §1.10) และต้องเก็บชื่อโปรเจกต์ซ้ำไว้ (`ProjectTitle`) |

### การเก็บข้อมูลซ้ำ (denormalization) โดยตั้งใจ

เพื่อให้ **ทุกฟิลเตอร์หลัก delegate ได้** และเพื่อเลี่ยง `LookUp()` ซ้อนใน gallery (ซึ่งยิง
request ต่อแถว) ลิสต์ลูกจึงเก็บค่าซ้ำจากแม่:

| คอลัมน์ซ้ำ | อยู่ใน | ที่มาของความจริง (owner) | ใครเขียน |
|---|---|---|---|
| `Department` | Phases, Tasks | `Projects.Department` | แอป ตอนสร้าง/ย้ายโปรเจกต์ |
| `ProjectTitle` | Phases, Tasks | `Projects.Title` | แอป ตอนสร้าง + ตอนเปลี่ยนชื่อโปรเจกต์ |
| `PhaseTitle` | Tasks | `Phases.Title` | แอป |
| `OwnerEmail` | Projects, Phases, Tasks | `Projects` → built-in **Created By (Author)** | แอป |
| `AssignedToEmail`, `PersonEmail` | Tasks, Phases | คอลัมน์ Person ในแถวเดียวกัน | แอป (เขียนเป็นตัวพิมพ์เล็กเสมอ) |

**กฎการดูแล:** แอปเขียนค่าซ้ำเหล่านี้ทุกครั้งที่ patch และหน้าจอ **Admin** มีปุ่ม
"ซ่อมข้อมูลอ้างอิง" ที่ไล่เขียนใหม่ทั้งลิสต์ เผื่อกรณีมีคนแก้ผ่าน SharePoint โดยตรง
สิทธิ์ความจริงอยู่ที่ตารางแม่เสมอ — ค่าซ้ำเป็นแค่สำเนาเพื่อความเร็ว

## 1.5 กลยุทธ์ Delegation (หัวใจของงานนี้)

### หลักการเดียวที่ใช้ทั้งแอป

> **ดึงด้วย query ที่ delegate ได้ 100% ให้ชุดข้อมูลเล็กพอก่อน → แล้วค่อยกรองละเอียดในหน่วยความจำ**

ชั้นที่ 1 (ส่งไป SharePoint — delegate ได้ทั้งหมด):

```
Filter(Tasks,
    Department = gblDept,          // text, indexed, =
    StartDate  <= gblWinEnd,       // date,  indexed, <=
    DueDate    >= gblWinStart      // date,  indexed, >=
)
```

ชั้นที่ 2 (ทำในเครื่อง บน collection ที่ถูกจำกัดขนาดแล้ว): ฟิลเตอร์หลายโปรเจกต์,
ฟิลเตอร์คน, ฟิลเตอร์สถานะ, ฟิลเตอร์แผนกของ BAU

ชั้นที่ 1 รับประกันว่าจำนวนแถวที่ไหลลงมาถูกจำกัดด้วย **ช่วงวันที่ + แผนก** ไม่ใช่ด้วย
data row limit และแอปมี **ป้ายเตือนภาษาไทย** เมื่อชุดข้อมูลแตะเพดาน (ดู `gblTruncated`)

### ตารางรูปแบบที่ห้ามใช้ และของแทนที่ใช้จริง

| รูปแบบที่ห้าม (ไม่ delegate บน SharePoint) | ใช้แทนด้วย | ใช้ที่ไหนในแอป |
|---|---|---|
| `Search(Tasks, txt, "Title")` | `StartsWith(Title, txt)` — delegate ได้บน SharePoint | หน้า Table, หน้า Skills |
| `Filter(Tasks, ProjectID in colSelected)` | ดึงตามช่วงวันที่ก่อน แล้ว `Filter(colTasks, ProjectID in colSel)` บน collection | ฟิลเตอร์โปรเจกต์แบบหลายค่า |
| `CountRows(Filter(Tasks, …))` ทั้งลิสต์ | นับบน collection ที่จำกัดช่วงแล้ว + ป้ายบอก "ในช่วงที่เลือก" | Dashboard ทุกตัวเลข |
| `CountIf(Tasks, …)` | เหมือนข้างบน | Dashboard |
| `LookUp(Projects, ID = ThisItem.ProjectID).Title` ใน gallery | คอลัมน์ `ProjectTitle` ที่เก็บซ้ำไว้ | ทุก gallery |
| `Filter(Tasks, AssignedTo.Email = x)` (sub-field ของ Person) | `Filter(Tasks, AssignedToEmail = x)` — text, indexed | My Tasks, ฟิลเตอร์คน |
| `Sort(…, Len(Title))` / ฟังก์ชันในเงื่อนไข | เก็บค่าที่คำนวณไว้เป็นคอลัมน์ | — |
| `Filter(list, IsBlank(col))` | `col = ""` (text) หรือ `col = Blank()` บน date — ตรวจคำเตือนใน Studio | Admin |

### จุดที่ delegate ไม่ได้จริง ๆ และวิธีรับมือ (แจ้งตรง ๆ)

| ข้อจำกัด | เหตุผล | วิธีที่ใช้ |
|---|---|---|
| ฟิลเตอร์ **แผนก** บน BAU | BAU ไม่มีคอลัมน์แผนก ต้องถาม Office 365 Users ทีละอีเมล | ดึง BAU ตามช่วงวันที่ (ชุดเล็ก) → map อีเมล→แผนกจาก `colProfiles` ที่ cache ไว้ → กรองในเครื่อง + ป้ายเตือนถ้าชุดข้อมูลแตะเพดาน |
| ฟิลเตอร์ **คน** บน BAU | ถ้า Responder/LM เป็น Person column การเทียบ `.Email` ไม่ delegate | กรองในเครื่องบนชุดที่จำกัดช่วงวันที่แล้ว (BAU ทั้งลิสต์ ~830 แถว ยังปลอดภัย) **และ** ถ้าเป็น Text column จะ delegate ได้ → ผมให้สูตรทั้งสองแบบ |
| **นับรวมทั้งลิสต์** (เช่น "งานทั้งหมดในระบบ") | `CountRows` ไม่ delegate | Dashboard นับเฉพาะ "ในช่วงวันที่ที่เลือก" และเขียนกำกับไว้ชัดเจนเป็นภาษาไทย ไม่หลอกว่าเป็นยอดรวมทั้งระบบ |
| **เลื่อนหน้า (paging) ข้าม 2,000 แถว** | SharePoint ไม่มี skip/offset ที่ delegate ได้ | หน้า Table ใช้ **keyset paging** บน `ID` (`Filter(..., ID > cursor)` + `SortByColumns(…,"ID")` + `FirstN(50)`) ทั้งหมด delegate ได้ และเดินได้ไม่จำกัดจำนวนแถว |

ทางเลือก C (ถ้าในอนาคตข้อมูลโตเกินนี้): เพิ่มลิสต์ `TimelineSummary` ที่เก็บ 1 แถวต่อโปรเจกต์
ต่อเดือน พร้อมตัวเลขสรุป แล้วให้ Dashboard อ่านจากลิสต์นั้น — ต้องใช้ Power Automate 1 flow
(รายคืน) ซึ่งตอนนี้ **ยังไม่จำเป็น** จึงไม่ใส่มา

### Delegation ต่อหน้าจอ

| หน้าจอ | query ที่ส่งไป SharePoint | กรองในเครื่อง | เพดานจำนวนแถว |
|---|---|---|---|
| Timeline | ช่วงวันที่ซ้อนทับ + แผนก (Projects/Phases/Tasks/BAU) | โปรเจกต์, คน, สถานะ, ประเภท | ตามระดับซูม: สัปดาห์ ≈ สิบ ๆ แถว, เดือน ≈ ร้อย ๆ, ไตรมาส ≈ พัน ๆ |
| Dashboard | ใช้ collection เดียวกับ Timeline | ทั้งหมด | เท่ากับ Timeline |
| Board | ใช้ collection เดียวกับ Timeline | จัดกลุ่มตามสถานะ | เท่ากับ Timeline |
| Table | keyset paging บน `ID` + ฟิลเตอร์ delegate ได้ | — | ไม่จำกัด (ทีละ 50 แถว) |
| Calendar | ช่วง = เดือนที่แสดง (delegate) | — | ≈ จำนวนงานใน 1 เดือน |
| My Tasks | `AssignedToEmail = me` (delegate) + BAU ตามช่วง | BAU: Responder/LM | เล็ก |
| Skills | `StartsWith(Title, คำค้น)` + `Department =` (delegate) | — | เล็ก |

## 1.6 ข้อความภาษาไทยส่งเจ้าของลิสต์ BAU (ขอ index)

> เรียนคุณ [ชื่อเจ้าของลิสต์]
>
> ทีมเรากำลังทำแอปติดตามไทม์ไลน์โปรเจกต์ และต้องการ **อ่านอย่างเดียว** จากลิสต์ [ชื่อลิสต์ BAU]
> โดยไม่แก้ไขข้อมูลหรือโครงสร้างใด ๆ
>
> รบกวนขอให้ช่วยเพิ่ม **index** ให้ 3 คอลัมน์นี้ครับ/ค่ะ: **StartDate**, **EndDate**, **Status**
>
> วิธีทำ: เปิดลิสต์ → ฟันเฟือง (Settings) → **List settings** → หัวข้อ Columns เลื่อนลงไปที่
> **Indexed columns** → **Create a new index** → เลือกคอลัมน์ → **Create** (ทำทีละคอลัมน์)
>
> เหตุผล: ปัจจุบันลิสต์มีประมาณ 830 รายการ เมื่อโตเกิน 5,000 รายการ SharePoint จะ

## 1.7 ตรวจสิทธิ์อ่านบน BAU โดยไม่แตะแอปอื่น

**วิธีที่ 1 (ผู้ใช้ทั่วไปทำเอง)** ส่ง URL ของลิสต์ให้ผู้ใช้เปิดในเบราว์เซอร์ ถ้าเห็นข้อมูล = มีสิทธิ์อ่าน
ถ้าเจอ "คุณไม่มีสิทธิ์เข้าถึง" = ยังไม่มีสิทธิ์ (การเปิดดูไม่เปลี่ยนแปลงอะไร)

**วิธีที่ 2 (เจ้าของลิสต์ตรวจให้)** List settings → **Permissions for this list** →
**Check Permissions** → ใส่ชื่อผู้ใช้ → ระบบจะบอกระดับสิทธิ์ ปุ่มนี้ **อ่านอย่างเดียว ไม่เปลี่ยนสิทธิ์**

**ในแอป** หน้าจอทุกหน้าที่ใช้ BAU จะตรวจ `gblBauReadable` ถ้าโหลดไม่สำเร็จจะขึ้นแถบสีเหลืองว่า
*"ไม่สามารถอ่านข้อมูล BAU ได้ — กรุณาติดต่อผู้ดูแลลิสต์เพื่อขอสิทธิ์ Read"* แทนที่จะแสดงหน้าว่างเปล่า

## 1.8 วันที่และ time zone (กันคลาดเคลื่อน ±1 วัน)

1. คอลัมน์วันที่ในลิสต์ใหม่ตั้งเป็น **Date Only** ทั้งหมด (ไม่เก็บเวลา)
2. ตั้ง time zone ของ SharePoint site เป็น **(UTC+07:00) Bangkok**
   (Site settings → Regional settings)
3. **ตอนเขียน** แอปจะยึดเวลาเที่ยงวันเสมอ: `DateAdd(dp.SelectedDate, 12, TimeUnit.Hours)`
   → UTC 05:00 ของวันเดียวกัน ไม่มีทางตกไปวันก่อนหน้า (ปัญหาคลาสสิกคือการเขียนเวลาเที่ยงคืน
   ซึ่งกลายเป็น 17:00 ของวันก่อนหน้าใน UTC)
4. **ตอนแสดง** ใช้ `Text(d, "d mmm yyyy", "en-US")` → `19 Oct 2026`
   **ต้องใส่ `"en-US"` เสมอ** ไม่งั้นเครื่องที่ตั้งภาษาไทยจะแสดงเป็น พ.ศ. และเดือนไทย ซึ่งไม่ตรงกับแอป L&D TMP
5. **ตอนเทียบ** ขอบเขตช่วงเวลาสร้างจาก `DateAdd(DateValue(...), 12, TimeUnit.Hours)` เหมือนกัน
   ทำให้เทียบกับค่าที่เก็บไว้ได้ตรงกัน

> หมายเหตุความถูกต้อง: พฤติกรรมการแปลง time zone ของ SharePoint connector กับคอลัมน์
> "Date Only" เปลี่ยนไปหลายรอบในอดีต ผมใช้วิธียึดเที่ยงวันเพราะปลอดภัยกับทั้งพฤติกรรมเก่าและใหม่
> ให้ยืนยันด้วย Test Case T-12 ในไฟล์ `05-verification-and-test-plan.md`

## 1.10 สิทธิ์ ความเป็นเจ้าของ และกรณีขอบ

**ในแอป** คุม 2 ชั้นเสมอ: `DisplayMode` (ปุ่ม/ฟอร์มเป็น View) และ `Visible` (ซ่อนของที่ทำไม่ได้)

**ที่ SharePoint** (เพราะผู้ใช้เปิดลิสต์ตรง ๆ ได้ แอปกันไม่ได้):

| ลิสต์ | ตั้งค่า | ผลลัพธ์ |
|---|---|---|
| Projects, Phases, Tasks | Advanced settings → Item-level permissions → Create and Edit = **"Create items and edit items that were created by the user"** | ผู้ใช้แก้ได้เฉพาะแถวที่ตัวเองสร้าง ซึ่งตรงกับกฎ "เฉพาะผู้สร้างโปรเจกต์แก้ได้" เพราะเฟสและงานทั้งหมดถูกสร้างโดยผู้สร้างโปรเจกต์คนเดียวกัน |
| | Read access = **"Read all items"** | ทุกคนดูไทม์ไลน์ของคนอื่นได้ |
| TaskTemplates | สิทธิ์ลิสต์: ทุกคน **Read**, admin group **Edit** | เป็น master data |
| SkillsInterests, AppAdmins | ตัดการสืบทอดสิทธิ์ → group `PP_Admins` = **Edit**, ทุกคน = **Read** | ตรงกับกฎ "เฉพาะ AppAdmins แก้ได้" |

### กรณีขอบและข้อแลกเปลี่ยน (ต้องรู้ก่อนใช้งานจริง)

1. **เจ้าของลาออก / ย้ายงาน** — บัญชีถูกปิด แถวยังอยู่แต่ไม่มีใครแก้ได้ (ยกเว้น site owner)
   แก้ได้ 3 ทาง:
   - (แนะนำ) หน้า **Admin** มีปุ่ม "โอนความเป็นเจ้าของโปรเจกต์" ที่เขียนทับ `OwnerEmail`
     โดยแอปตัดสินสิทธิ์จาก `OwnerEmail` **ไม่ใช่** `Author` → โอนได้โดยไม่ต้องแตะ SharePoint
     **แต่** ที่ชั้น SharePoint เจ้าของเดิมยังเป็น Author อยู่ คนใหม่จึงแก้ผ่านหน้าลิสต์โดยตรงไม่ได้
     (แก้ผ่านแอปได้ปกติ) — นี่คือข้อแลกเปลี่ยนที่ยอมรับ
   - site owner แก้ค่า Author ผ่าน PnP (`Set-PnPListItem -Values @{Author=...}`) ให้ตรงกันทั้งสองชั้น
   - ปล่อยไว้และให้ admin เป็นคนแก้แทน
2. **ผู้ที่ถูกมอบหมายงานแก้สถานะงานตัวเองไม่ได้** — เป็นไปตามข้อกำหนด ("ทุกคนที่ไม่ใช่ผู้สร้างดูได้อย่างเดียว")
   ผลข้างเคียง: กระดาน Kanban จะเปลี่ยนสถานะได้เฉพาะเจ้าของโปรเจกต์ ถ้าภายหลังอยากให้ผู้รับผิดชอบ
   เปลี่ยนสถานะเองได้ ต้องเปลี่ยน item-level permission เป็น "Create and edit all items"
   แล้วไปพึ่งการคุมสิทธิ์ในแอปเพียงชั้นเดียว (อ่อนแอกว่า) — แนะนำให้คุยกันก่อนเปลี่ยน
3. **admin ของแอป ≠ site owner** — คนที่อยู่ในลิสต์ `AppAdmins` เห็นหน้า Admin ในแอป
   แต่ถ้าไม่ได้อยู่ใน SharePoint group `PP_Admins` ด้วย จะกดบันทึกแล้วเจอ error สิทธิ์
   **ต้องใส่ชื่อทั้งสองที่เสมอ** (สคริปต์ PnP เตือนเรื่องนี้ไว้แล้ว)
4. **ลบโปรเจกต์แบบ cascade** — SharePoint ไม่มี cascade delete แอปจึงลบลูกเองตามลำดับ
   งาน → เฟส → โปรเจกต์ ถ้าลบไม่ครบ (เน็ตหลุดกลางทาง) จะเหลือ "งานกำพร้า"
   หน้า Admin มีปุ่ม **"ตรวจหางานกำพร้า"** สำหรับกรณีนี้
   และ `RemoveIf` ทำได้ครั้งละไม่เกิน 2,000 แถว แอปจึงวนลบและแสดงจำนวนที่เหลือจนกว่าจะหมด
5. **ผู้ใช้ไม่มีค่า department ใน profile** — ฟิลเตอร์แผนกจะตั้งค่าเริ่มต้นเป็น "ทุกแผนก"
   พร้อมข้อความไทยบอกเหตุผล ไม่ปล่อยให้หน้าจอว่างโดยไม่รู้สาเหตุ (Test Case T-15)
